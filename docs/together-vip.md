# 一起听：会员音源共享怎么做、怎么验证、怎么排错

这份文档只讲一件事：**房间里只有一个人有 QQ 音乐会员，两个人怎么都能听会员歌**，包括"没有会员的那个人点歌"。实现分布在三层：

```
QQ 音乐账号 ──签 vkey 直链──> 会员端 Lilt ──stream 消息──> 房间服务（DO）──> 另一端 Lilt
                                  │                                              │
                     └── 各自向 QQ CDN 取流：会员取自己的，没有会员的那端取房间链接 ──┘
```

## 1. 为什么这样能成立

- QQ 签出的播放直链（`vkey`）是发给"请求它的账号"的，但**直链本身不校验谁在播放**；拿到链接的人都能下载同一份音频。
- 所以房间**不需要共享账号，也不需要把会员 Cookie 放到服务器**，只需要共享一条链接。
- 音频永远不经过房间服务器：服务器只转发控制信令和链接，两端各自从 QQ CDN 取流。这样既省流量，也不会因为服务器在国外而变慢。

## 2. 三种供源方式（按优先级）

1. **播放器顺手分享**：任何成员的播放器解析出当前歌曲的完整直链，就在 1 秒内发 `stream`；服务端按曲目缓存（40 分钟 / 最近 40 首），新进房的人在 `welcome` 的 `streams` 里直接拿到。
2. **收到请求代签**：某一端播不出来会发 `stream.request`；服务端先把手上那条直接回给它；其他成员收到后，**用自己的账号当场调 `songurl` 签一条**（每曲 15 秒最多一次）。所以会员那台**即使没在播这首歌、播放器暂停或空闲**也能供源。
3. **点歌台链路**：非会员在点歌台点歌 → 任何成员点"播放" → 服务端广播 `play` → 房主队列切歌 → 两端跟随锚点；会员端解析/代签并分享，非会员端直接用。

## 3. 试听版：这个功能最容易翻车的地方

QQ 对没有权限的账号，很多时候**不报错，而是给 30 秒试听**，但接口里的 `size` 仍是整首大小。如果直接播，会出现"一个人 30 秒后停了、另一个人还在放"。

处理方式：

- 只对 `fee=1`（会员）和 `fee=4`（购买）的曲子做真实长度探测：`Range: bytes=0-1`，读 `Content-Range` 的总长度；
- 真实长度不足整首一半 → 标记 `Trial`；
- **试听不分享、不进缓存**；
- 房间里有别人时，拿到试听**不放**：先等 4 秒房间的完整链接，等不到就报"需要 VIP"并停在房间的这首歌上（不会自动跳下一首，避免和房间锚点打架）；完整链接一到会自动重载并继续；
- **每个账号优先用自己签的链接**，只有签不出来的那一端才用房间里的链接。这样"两个会员"不会互相用对方的 vkey，听起来就是"我在房间里放，他刚好也听到了"；两端的进度差由锚点每秒校正。

## 4. 已经处理掉的坑

| 坑 | 处理 |
|---|---|
| 非会员收到 30 秒试听还当整首播 | `Range` 探测真实大小 + `Trial` 标记，房间里拒播试听 |
| 试听被缓存成整首 | 试听走临时文件，永不 `keep`；旧版本留下的异常缓存会被丢弃 |
| 两个会员各有一条链接，每秒互相覆盖 | 房间已有链接时不再主动出价；只有收到 `stream.request` 才用自己的一条重新出价 |
| 会员端播放器空闲/暂停，签不出链接 | `stream.request` 触发**当场调接口代签**，不依赖本机播放器状态 |
| 会员端在房间但没登录 | 签不出来，界面提示需要 VIP；不影响其他功能 |
| 晚进房的人要等别人分享 | `welcome` 直接带 `stream` + `streams` |
| 同一首歌换个房间/重进房间链接丢了 | 客户端共享表 45 分钟；服务端缓存 40 分钟、最近 40 首 |
| 房间成员让别人的客户端取任意地址 | 服务端只接受 `*.qq.com` / `*.qqmusic.qq.com` 的链接，否则 `bad_stream` |
| CDN 因缺 Referer 返回 401/403 | 下载与探测都带 `Referer: https://y.qq.com/` 重试一次 |
| 播放失败后客户端自动跳下一首，和房间错位 | 房间内（>1 人）不自动跳，停在原曲等链接 |
| 房主转让后没人供源 | 供源跟账号走，不跟房主走；新房主/任何成员都能签 |
| 旧版服务端 | 缺 `stream2` 时退回聊天隐藏分片；缺 `streams` 只是没有缓存补发 |

## 5. 部署与配置

房间服务（Cloudflare Worker + Durable Object，已部署到 `together.bdprk.com`）：

```bash
cd together
node node_modules/wrangler/bin/wrangler.js deploy
```

客户端默认连接 `wss://together.bdprk.com`；设置里"房间服务器"留空即用默认值。两端必须是**同一台房间服务**。

端到端自检（建房、同步、链接分享、缓存、署名、外链拒绝、晚进房、踢人、结束房间）：

```bash
go run ./cmd/together-probe -relay https://together.bdprk.com
```

本地联调：

```bash
cd together && npx wrangler dev --ip 127.0.0.1 --port 8787
go run ./cmd/together-probe -relay http://127.0.0.1:8787
```

## 6. 两个人怎么验

一台电脑也能验：新版本支持独立配置档，两个 Lilt 可以同时开、各登各的号，设置、登录态、缓存和单实例锁都是分开的。

- 桌面上的「Lilt 副号」快捷方式 = `Lilt.exe --profile guest`；
- 或者任意快捷方式加参数 `--profile guest`，也可以用环境变量 `LILT_PROFILE=guest`；
- 主号的配置在 `%APPDATA%\Lilt`，副号在 `%APPDATA%\Lilt guest`，互不影响。

1. A 登录**会员**账号，B 登录**非会员**账号（或干脆不登录），都打开 Lilt → 一起听。
2. A 建房，把 8 位房间号给 B；B 加入。
3. **验主动分享**：A 播一首 VIP 歌。B 端应显示「音源来自「A」的会员」，并且能完整播完（不是 30 秒）。
4. **验点歌代签**：B 在点歌台搜一首 VIP 歌 → 点歌 → 点"播放"。切歌后 B 仍应完整播放；A 端即使暂停着，也会在 1–2 秒内把链接供出去。
5. **验晚进房**：B 退出再进同一房间，正在播的 VIP 歌不应该重新等。
6. **验反向**：只有 B 是会员、A 不是，重做 3–4，结论应一样。

## 7. 排错

| 现象 | 先看什么 |
|---|---|
| B 端 30 秒就停 | 是不是两端都在新版本？B 端界面应显示「只拿到试听片段」，说明房间里没人能签；确认 A 的会员是否过期、A 是否还在房间 |
| B 端提示"需要 VIP"但 A 是会员 | A 端看是否在线、是否显示同一个房间；A 的 QQ 登录态是否有效；试试点歌台的"播放"再等 2 秒 |
| 一直"同步中…" | 房间连接断了；看顶部提示与设置里的房间服务器 |
| 两个人进度差几秒 | 两个人可能各自用自己的链接（码率不同）或网络卡；锚点每秒校正，超过 400ms 才 seek。若其中一人一直用另一人的链接，检查他是否签不出这首歌 |
| 链接过一段时间失效 | vkey 有有效期；播放失败会自动发 `stream.request`，会员端会重新签 |
| 部署后旧客户端行为不变 | 旧客户端没有 `stream2`/`streams`，走聊天分片；升级两端即可 |

## 8. 边界（必须知道）

- **供源机必须在线**：有会员的那台 Lilt 要开着并连着房间；它退出后房间在宽限期结束，期间没人能签新歌。
- **服务器不持有账号**：不在云端保存 Cookie，也不做账号池；这是安全边界，也是这套方案能长期用的原因。
- **QQ 的风控**：同一账号短时间内大量签链接可能被限；代码里每曲 15 秒最多签一次，正常两个人听歌远低于阈值。
- **CDN 按 IP 拒绝的极端情况**：已带 Referer 重试；如果某个网络环境仍然拒绝，只能由供源端换网络/换账号，链接本身无法绕过 IP 限制。
## 9. 安全性：哪些东西会离开这台电脑

| 数据 | 去哪里 | 说明 |
|---|---|---|
| QQ 登录态、Cookie、密码 | **不离开本机** | 房间协议里没有任何账号凭据 |
| 签好的单曲直链（含 vkey） | 房间服务器（Cloudflare DO） | 只对那一首歌有效，有有效期；拿到的人能听这一首，不能登录、不能改资料、不能代表账号做别的。链接的查询串里可能带 QQ 号（uin）、guid 等参数，房间成员与服务器能看到；不含登录凭据 |
| 昵称、头像、歌曲信息、聊天、点歌 | 房间服务器 | 房间码是唯一门槛，最多 10 人 |
| 音频本身 | **不经过服务器** | 两端各自向 QQ CDN 取流 |

### 像不像"一个人在放歌"

- **不改 QQ 音乐协议**：只用原有的 `SongURL` 签链接，没有新增/伪造接口参数，没有改 UA、Cookie、Referer 之外的东西。
- **每个账号用自己的签名**：会员两端各播各的链接，QQ 看到的是两个账号各自正常播放；只有没有会员的那一端才复用房间里的那条链接。
- **不主动多要链接**：只有"另一端明确发来 `stream.request`"时才代签一次；同一首歌被拒绝后 10 分钟内不再问 QQ。
- **试听探测只在房间里做**：普通播放的请求数量和以前完全一样。
- **沿用原有的 UA 与请求节奏**：房间同步、心跳、进度校正都发生在自己的服务器上，不增加 QQ 侧的连接；每首歌的 QQ 请求接近普通播放。

### 已经做的防护

- **身份不暴露**：房间列表里显示的是句柄（房间密钥的哈希），不是客户端重连用的私有 ID；拿句柄加入房间不会变成房主、不会顶掉别人。房主的 `hostKey` 走 HTTP header，不放进 URL（代理/日志更容易留下 query）。
- **只服务原生客户端**：带 `Origin` 的请求（浏览器）在 `/room` 与 `/ws` 上直接 403，页面无法顺带把访客变成房间创建者；CORS 不再放开。
- **按 IP 限速**：建房 10 次/分钟、查房 60 次/分钟、连接 30 次/分钟（每个 isolate），外加建房 60 次/分钟的总闸；URL 超过 2048 字节直接 414。
- **链接只收 QQ CDN**：服务端只接受 `*.qq.com` / `*.qqmusic.qq.com`，客户端收到链接还会再验一次真实长度，防止被指向任意地址或把试听当整首。
- **封面/头像只取 QQ 域名**：服务端和客户端都过滤，房间成员不能借别人的客户端去请求任意 URL。
- **明文房间服务器只允许本机**：公网必须 `wss://`/`https://`，避免直链在网络上裸奔。
- **限速与上限**：每连接 20 条/秒；同一首歌的分享 1 次/2 秒；求链接的广播 1 次/2 秒；建房每个 isolate 60 次/分钟；成员 10、点歌 50、聊天 100 条。
- **试听不进缓存、不分享**：避免把 30 秒片段当成整首留在磁盘上。
- **房间即焚**：房主结束/退出、空置 24 小时、房主失联 2 分钟，房间与其中的链接、聊天一起删除。

### 仍然要注意的

1. **房间码就是钥匙**：8 位、32 字母表（约 1.1 万亿种），不要发到公开群；被陌生人拿到，他就能进房听歌、看聊天、拿直链。
2. **拿到直链的人能听那一首**：不要在不信任的房间里分享会员链接；链接有效期由 QQ 决定，不能提前吊销。
3. **服务器运营者能看到链接**：这是"晚进房也能听"的代价。如果不接受，自己部署一份（数据在你自己的 Cloudflare 账号）或用可信的服务器。
4. **QQ 侧风控**：同一账号签出的链接被另一个 IP 播放，理论上可能被 QQ 视为异常（限流/风控）。代码无法消除这一点；建议只和熟人一起听，不要把房间当公开电台。
5. **Cloudflare 侧建议**：在控制台给 `POST /room` 和 `/ws` 加一条按 IP 的限速规则（例如 60 次/分钟），比 Worker 里的单 isolate 限速更有效。

### 如果你要把房间服务器换掉

客户端设置里的"房间服务器"填 `wss://你的域名`；本机调试可以填 `http://127.0.0.1:8787`（明文只允许本机）。换服务器不会影响账号安全，但两端必须填同一个。
